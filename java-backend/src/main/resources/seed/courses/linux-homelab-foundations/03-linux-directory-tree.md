## 3.1 One tree, many possible storage devices

Linux presents one unified pathname tree beginning at /. There are no drive letters. A filesystem on the VM disk provides the initial root tree. Other filesystems—another partition, a USB disk, a network export or a temporary in-memory filesystem—are attached at directories called mount points. After attachment, applications use normal paths and usually do not need to know which device or server supplies the bytes.

```bash
/
|-- home
|   `-- anikesh348        personal files and user configuration
|-- etc                   host-wide configuration
|-- var                   changing state: logs, caches, databases
|-- usr                   installed programs, libraries and shared data
|-- srv                   data served by this host / deployment convention
|-- run                   current-boot runtime state
|-- tmp                   temporary shared workspace
|-- proc                  live process/kernel view, not ordinary disk files
|-- sys                   live kernel/device model, not ordinary disk files
|-- dev                   device nodes
|-- root                  root user's private home
`-- mnt, media            conventional attachment points
```

> The slash has two jobs
> A leading slash means 'begin at filesystem root'. Slashes inside a path separate directory names. The path /var/log/syslog therefore means: start at /, enter var, then log, then locate syslog.

## 3.2 The important directories, in plain language

| Path | What normally belongs there | Examples / warning |
| --- | --- | --- |
| / | The top of the visible tree | Do not treat it as a workspace or place arbitrary files here |
| /home | Home directories for regular human accounts | /home/anikesh348; permissions may prevent other users entering |
| /root | The root account's home directory | Not the same as /; normally mode 700 |
| /etc | Host-wide configuration chosen by the administrator | /etc/fstab, /etc/ssh, /etc/systemd; usually root-owned |
| /var | State whose size/content changes during normal operation | /var/log, /var/lib, /var/cache, /var/tmp |
| /usr | Most installed programs, libraries and read-only shareable data | /usr/bin, /usr/lib, /usr/share; not 'user home' |
| /bin, /sbin | Essential command paths; usually links into /usr on modern Ubuntu | /bin -> usr/bin and /sbin -> usr/sbin |
| /usr/local | Software installed locally by the administrator | Kept separate from distro-managed /usr files |
| /opt | Self-contained optional third-party packages | A vendor application may own /opt/vendor-app |
| /srv | Data or deployments served by this machine, by local convention | Your homelab uses /srv for deployments and media mount paths |
| /run | Small runtime state for the current boot | PID files and sockets; usually tmpfs and recreated after reboot |
| /tmp | Short-lived files shared by many users | Mode 1777; sticky bit restricts deletion; do not assume persistence |
| /var/tmp | Temporary files intended to survive reboot longer than /tmp | Still not permanent application storage |
| /proc | Virtual live view of processes and kernel values | /proc/123/status, /proc/meminfo; generated by kernel |
| /sys | Virtual model/control surface for devices and kernel subsystems | /sys/class, /sys/fs/cgroup; write only with understanding |
| /dev | Device nodes representing kernel-managed devices | /dev/sda1, /dev/null, /dev/dri/renderD128 |
| /mnt | Administrator-chosen temporary or explicit mounts | Convention only; not automatically mounted |
| /media | Removable media, often mounted by desktop software | Not the same as Jellyfin's container /media path |

> A convention is not enforcement
> Linux does not technically stop you from placing a script in /etc or logs in /usr. The directory conventions make systems predictable for humans, packages, backups and security policies. Breaking them creates operational confusion even if the kernel permits it.

## 3.3 Configuration, persistent state, cache, logs and runtime state

When operating an application, classify each file by purpose. This tells you what must be backed up, what may be regenerated, what must remain writable and what disappears at reboot.

| Category | Meaning | Common location | Backup expectation |
| --- | --- | --- | --- |
| Configuration | Administrator's intended settings | /etc or deployment directory | Usually yes; protect secrets separately |
| Persistent state | Data produced by the application that matters later | /var/lib, volume or bind mount | Yes; test application-consistent restore |
| User data | Documents, media and user-created content | /home, /srv, storage mount | Yes; often the most valuable bytes |
| Logs | Historical events useful for diagnosis/audit | /var/log or logging backend | Retention policy; not always full backup |
| Cache | Recreatable acceleration data | /var/cache or app cache directory | Normally no, if truly recreatable |
| Runtime state | Sockets, PIDs and locks valid for this boot/process | /run or tmpfs | No; must be recreated |
| Temporary data | Short-lived working files | /tmp, /var/tmp or app tmp | Normally no; define cleanup and size bounds |

A Docker container's writable layer is usually disposable. Important configuration and state must be in declared bind mounts or volumes. A backup that captures only the Compose YAML but not the application's database is incomplete; a backup that captures only data but not the key required to decrypt it is unusable.

## 3.4 Your home directory and its default contents

The account record selects /home/anikesh348 as your home. Bash expands ~ and $HOME to this path. It is the safe default place for your personal files, source code and user-level configuration. It is not automatically shared with other accounts.

| Name | Purpose | Important detail |
| --- | --- | --- |
| ~/.bashrc | Bash settings for interactive non-login shells | Aliases, prompt and shell options; invalid syntax can affect new terminals |
| ~/.profile | Login/session environment | Often loads .bashrc and establishes PATH additions |
| ~/.ssh | SSH client keys, known hosts and optional config | Must be tightly permissioned; never print private keys |
| ~/.config | Per-user application configuration | systemd user units live under ~/.config/systemd/user |
| ~/.local/bin | Per-user executable scripts/programs | Runs without changing system-wide /usr/local/bin |
| ~/.local/share | Per-user application data | May contain important persistent state |
| ~/.cache | Per-user recreatable cache | Can grow; should not contain the only copy of important data |
| ~/Documents | A conventional personal content directory | A server install may not create all desktop-style directories |

> Hidden does not mean protected
> A filename beginning with dot is omitted by a default ls. That is only a display convention. Permissions—not the leading dot—control access.

### Inspect home without exposing secrets

The find command prints only names directly below home. It does not read file contents. The explicit depth bound prevents a recursive crawl through caches, repositories or secrets.

```bash
printf 'home=%s\n' "$HOME"
ls -ld "$HOME"
find "$HOME" -maxdepth 1 -mindepth 1 -printf '%f\n' | sort | sed -n '1,30p'
```

> Why this matters in your homelab
> Listing names is often enough to locate a project. Do not print .env, key, token or credential contents while exploring.

## 3.5 File type, pathname and inode are different ideas

A pathname is a sequence of directory entries used to locate an object. On a typical Linux filesystem, the object's inode stores its type, permissions, ownership, timestamps and pointers to data. The filename is stored in its parent directory, not inside the file itself. This explains why directory permissions control renaming and deleting names.

| First ls -l character | Object type | What it represents |
| --- | --- | --- |
| - | Regular file | Bytes such as text, an executable, image or database |
| d | Directory | A mapping from names to filesystem objects |
| l | Symbolic link | A small object containing another pathname |
| c | Character device | Byte-stream device interface, for example a terminal |
| b | Block device | Random-access block device, for example a disk |
| s | Socket | Local inter-process communication endpoint |
| p | Named pipe/FIFO | A named byte stream between processes |

## 3.6 Hard links and symbolic links

A hard link is another directory entry referring to the same inode. Both names are equally real, and the data remains until the final hard link is removed and no process holds it open. Hard links normally cannot cross filesystems and ordinary users cannot hard-link directories. A symbolic link is a separate object containing a pathname; it can cross filesystems but may become broken if the target moves.

### Hands-on lab: see names, inodes and links

> Safety
> Run this lab on hp-codex. It writes only inside ~/linux-foundations-lab.

Step 1 - Create one regular file

The directory gains an entry original.txt referring to a new regular-file inode.

```bash
mkdir -p ~/linux-foundations-lab/module-3/links
cd ~/linux-foundations-lab/module-3/links
printf 'one set of bytes\n' > original.txt
```

Step 2 - Create two kinds of links

ln without -s creates a hard link; -s creates a symbolic link storing the target text.

```bash
ln original.txt hard-name.txt
ln -s original.txt symbolic-name.txt
```

Step 3 - Compare metadata

The two hard-linked names share an inode and link count. The symlink has a different inode and type.

```bash
ls -li
stat -c 'inode=%i links=%h type=%F name=%n' original.txt hard-name.txt symbolic-name.txt
```

Step 4 - Rename the original name

The hard name still reaches the inode. The relative symbolic link still contains original.txt, which no longer exists, so it is broken.

```bash
mv original.txt renamed.txt
cat hard-name.txt
cat symbolic-name.txt 2>&1 || true
readlink symbolic-name.txt
```

> What success looks like
> You can explain why hard-name.txt still works and symbolic-name.txt fails after the rename, without saying that the bytes were copied.

## 3.7 Mounts attach another filesystem at a directory

Before a mount, a mount-point directory belongs to its parent filesystem and may contain ordinary entries. While another filesystem is mounted there, those old entries are hidden—not deleted—because pathname lookup crosses into the mounted filesystem. After unmount, the underlying entries become visible again. This is why writing application data into an unmounted NFS mount point is dangerous: it can silently fill the VM's local disk.

### Resolve the filesystem behind a path

findmnt -T resolves the mount containing a path. df reports filesystem capacity, not the sum of file sizes. stat -f reports filesystem-level metadata.

```bash
findmnt -T /home/anikesh348 -o TARGET,SOURCE,FSTYPE,OPTIONS
df -hT /home/anikesh348
stat -f -c 'filesystem=%T blocks=%b free=%f' /home/anikesh348
```

Typical output

```bash
/      /dev/sda1  ext4  rw,relatime,...
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/sda1      ext4   24G  ...   ...   ...  /
```

> df versus du
> df asks the filesystem about allocated/free blocks. du walks reachable directory entries and totals their allocated blocks. Open-but-deleted files, permissions, mount boundaries, hard links and sparse files can make their answers differ.

## 3.8 Trace your Jellyfin media path

| Layer | Path / mechanism | What it means |
| --- | --- | --- |
| Physical storage host | pi-purva: /dev/sda2 ext4 | The authoritative local filesystem containing bulk media bytes |
| NFS server namespace | pi-purva: /srv/data/media | The directory exported by the Pi's NFS server |
| NFS client namespace | ubuntu-purva: /srv/data/media | A client mount whose operations travel to pi-purva |
| Docker bind mount | host /srv/data/media -> container /media | Jellyfin sees the client-mounted tree under a container pathname |
| Application | Jellyfin reads /media/... | The application need not know the host calls it /srv/data/media |

The same text /srv/data/media has different storage semantics on each host. On pi-purva it is local authoritative storage; on ubuntu-purva it is a network-client view. Inside the container the path changes to /media. Always record host + namespace + path + resolved mount.

### Read-only: prove each live layer

The first command proves which filesystem supplies ubuntu-purva's path. Docker inspect proves the host-to-container mapping. The Pi command proves the filesystem behind the server path. These commands observe; they do not remount or change storage.

```bash
ssh ubuntu-purva 'findmnt -T /srv/data/media -o TARGET,SOURCE,FSTYPE,OPTIONS'
ssh ubuntu-purva \
+  'sudo docker inspect jellyfin --format "{{json .Mounts}}"'
ssh pi-purva 'findmnt -T /srv/data/media -o TARGET,SOURCE,FSTYPE,OPTIONS'
```

> Why this matters in your homelab
> If Jellyfin is empty, trace these transitions before changing library configuration or creating directories.
