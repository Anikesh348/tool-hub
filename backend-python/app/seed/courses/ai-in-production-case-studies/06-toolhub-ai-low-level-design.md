## 6.1 Four applications, one gateway, four different shapes

All four features call the exact same `routed_gateway_request()` from Lesson 5.3. Everything below this lesson's title is about what differs — and every difference is a deliberate response to that application's own traffic pattern, not an inconsistency:

| Application | Dispatch mechanism | Capability profile | Persistence |
| --- | --- | --- | --- |
| AI Assistant (`ai_chats.py`) | FastAPI `BackgroundTasks` (shared default thread pool) | `read-only` | Shared `ai_chats`/`ai_messages` |
| Course Q&A (`courses.py`) | Background pending→answered record | `knowledge-only` | `course_questions` |
| LeetCode AI (`leetcode_ai.py`, `leetcode_set_wizard.py`) | **Dedicated** `ThreadPoolExecutor(max_workers=4)` | `knowledge-only` | Isolated `leetcode_ai_chats`/`leetcode_ai_messages`, `leetcode_question_sets`, `leetcode_set_jobs` |
| MovieHub chat (`moviehub_chat_routes.py`) | `asyncio.to_thread` around a mostly-synchronous handler | `knowledge-only` | In-memory `moviehub_conversations` (slot-filling state, not chat history) |

## 6.2 The AI Assistant: the simplest, general-purpose case

`ai_chats.py` implements the canonical begin/complete-in-background pattern: `begin_message()` inserts the user's message and flips the chat's `runStatus` to `"running"`, and the route hands `complete_message_safely()` to FastAPI's built-in `BackgroundTasks`, which runs it on Starlette's shared default thread pool. The frontend polls `GET` on the chat until `runStatus` returns to `"idle"`. Using the *shared* thread pool here is a deliberate, reasonable choice, not an oversight: the Assistant is a single, general-purpose feature with comparatively low concurrent volume (a handful of admins), so there's no strong reason to isolate its executor from the rest of the application's default background-task pool the way a higher-traffic or more failure-sensitive feature might need to.

## 6.3 Course Q&A: knowledge grounded in the exact module the user is reading

`courses.py`'s question flow is `knowledge-only` because it needs zero infrastructure access — the answer should come entirely from the lesson content itself. Before calling the gateway, `_relevant_module_context()` does its own small retrieval step: it splits the current module's markdown into paragraph-sized blocks, ranks them by how many of the question's meaningful words (with common stop-words filtered out) they contain, and assembles an outline plus the highest-ranked blocks within a fixed character budget (`AI_CONTEXT_BUDGET`). This is a lightweight, keyword-based analog of the semantic RAG retrieval in Course 2, Lesson 4 — same goal (only send the model the parts of a larger document that are actually relevant to this question), simpler mechanism (term overlap instead of embeddings) because the corpus for any single question is one lesson's worth of markdown, not millions of documents, so the precision embeddings buy isn't worth the added infrastructure here. This is a good, real example of Course 2, Lesson 4's implicit lesson: RAG is a pattern with a spectrum of implementations, not one fixed technology stack — and a system should match retrieval complexity to corpus size, not default to the most sophisticated option available.

## 6.4 LeetCode AI: the most infrastructure-heavy of the four, for a specific reason

LeetCode AI gets its **own** `ThreadPoolExecutor(max_workers=4, thread_name_prefix="leetcode-ai")` — deliberately not sharing `ai_chats.py`'s background tasks or persistence — for two compounding reasons: first, isolation, so a burst of LeetCode AI activity can never starve the general Assistant's background tasks or vice versa (zero blast radius between features, echoing Course 3, Lesson 2.6's principle of scoping guardrails/resources to the actual risk); second, it has meaningfully more to do per request than a plain chat reply. Its "generate N questions" feature instructs the model (via `SYSTEM_PROMPT`) to return a fenced JSON block of proposed LeetCode slugs, which the backend then **re-resolves against LeetCode's real GraphQL API** — rejecting any slug that doesn't actually resolve, a concrete, load-bearing instance of Course 3, Lesson 2.3's "never let the model's own claim be treated as ground truth" principle, applied to *problem existence* rather than order status or product specs, but the identical pattern.

It also has to solve a subtler grounding problem: `_tracked_questions_context()` explicitly feeds the model a list of what the user has already tracked (capped at `MAX_TRACKED_CONTEXT_CHARS = 5500`, combined with the system prompt kept under the gateway's own ~8000-character ceiling). Without this, the model has no visibility into the user's tracker and reliably proposes well-known problems for a topic that turn out to already be tracked — a real, previously-confirmed failure mode (5 of 5 proposed slugs already tracked, before this context was added), and a concrete illustration of Course 1, Lesson 6.1's point: a model only "knows" what's actually in its current context window, never what's true about the world outside it.

The **question-set generation wizard** (`leetcode_set_wizard.py`) goes a step further than the free-text chat bubble: it's a genuine two-phase configure → preview → generate flow (`begin` → poll a job → `confirm`), where candidate questions are resolved and shown to the user for review **without being written to Mongo** until the user explicitly confirms — a human-approval checkpoint sitting structurally between generation and persistence, the same principle as Course 2, Lesson 3.4's human-in-the-loop graph interrupt, implemented here as an explicit unconfirmed-job document rather than a graph-level pause.

## 6.5 MovieHub chat: the case where the LLM is a fallback, not the default path

MovieHub's chat handler inverts the usual assumption that "an AI chat feature" means every message goes to an LLM. `resolve_chat_intent()` runs an ordered list of regex patterns against the user's message *first*; the LLM (`openai_json`, despite the name, calling the same `routed_gateway_request`) is only invoked to classify intent when every regex fails to match. Once an intent is known, the actual work — searching the media library, checking download status, approving a request — is deterministic application logic with no LLM involvement at all; the LLM reappears only for `openai_text`-based summarization of already-fetched, real download-status facts, with an explicit system instruction: *"Use only the supplied facts. Do not invent titles, progress, ETA, or completion state."* This is Course 3, Lesson 2.3's "ground every fact-sensitive claim in a real system, use the LLM purely for the language layer" principle, enforced directly in the prompt as well as architecturally by only ever handing the model already-fetched facts to summarize, never asking it to state a fact itself.

This is also *why* MovieHub's handler can get away with `asyncio.to_thread` around a synchronous function rather than a full background-task-plus-poll cycle: because most turns never call the LLM at all (a regex match resolves them essentially instantly), and the ones that do involve at most one single-shot classification or summarization call — a fundamentally lower and more bounded latency profile than LeetCode AI's open-ended, potentially multi-paragraph conversational replies, which justifies a different point on the sync/async spectrum from Course 3, Lesson 1.6, made deliberately rather than by accident.

## 6.6 What this comparison actually teaches

Looking at all four side by side, the reusable lesson isn't "always isolate your executor" or "always use background+poll" — it's that **each application's designer matched its infrastructure investment to its actual traffic and risk profile**: shared resources where isolation wasn't worth the complexity (Assistant), the lightest possible retrieval mechanism that still solves the problem (Course Q&A), full isolation plus a re-validation and human-confirmation step where the feature writes real data on the model's say-so (LeetCode AI), and an LLM-as-fallback design where a fast deterministic path handles the overwhelming majority of traffic (MovieHub). Reusing the shared gateway/router (Lesson 5) meant none of these four had to re-solve provider selection, failover, or capability enforcement — but none of them uncritically reused another feature's *application-level* design either, which is the more transferable takeaway for any system built on top of a shared internal platform.
